Operating problem

Tasks could not become a disconnected to-do list.

The client needed a controlled project operating model: general project visibility, personal task execution, a personal calendar that separates due dates from scheduled work, clear responsibility and access roles, escalation handling, project-level SharePoint links, task-level working attachments, and leadership visibility into the whole portfolio.

Client requirements

The project/task relationship is mandatory.

The reconstruction now reflects the client's actual operating rules rather than a generic PM template. A task always belongs to a project. If work is ad hoc, it still belongs to a departmental project so ownership, deadlines, escalation, files, and reporting remain traceable.

Project view · general

Projects expose one Project Owner, multiple Collaborators, multiple Informed users, project status, project due date, department, project timeline, project-level SharePoint folder, and access-scoped project Updates/chat.

Task view · personal

Tasks are connected to exactly one project and can be filtered by person, project, status, priority, due date, and scheduled work. The Responsible person is singular and must be either the project owner or one of the project's collaborators.

Calendar · due vs scheduled

Task and project due dates remain authoritative deadlines. Optional personal calendar scheduling is a separate work-planning layer: scheduling time to work on a task does not change its due date.

Priority override

Tasks have a single Priority field used when something must take precedence over the normal schedule. Priority does not replace the task's project connection or due date.

Escalation

A task can be escalated to another person only with an escalation note. Open escalations are surfaced in dashboard views so the recipient and leadership can see the issue without searching the full task board.

Communication & files

Project conversation uses access-scoped project Updates/chat and may reference tasks from that same project. Permanent project files link to Microsoft SharePoint at project level; task attachments are for temporary working files, screenshots, and execution evidence.

Leadership visibility

Leadership dashboards cover all projects with filters for active, closed, and future work, plus direct visibility into overdue projects/tasks and open escalations.

Phase 2 roadmap

Recurring tasks, stronger department-level organization, project/task dependencies, and company-wide agenda visibility are explicitly separated as Phase 2 rather than presented as completed Phase 1 functionality.

Architecture

One connected operating model.

Monday.com remains the business interface and record layer. Native Monday functionality handles views, dates, status, priority, people, updates, files, links, and dashboard surfaces; n8n and the Monday API are reserved for cross-board validation, append-only session control, aggregation, and technical audit logic.

Rate history is separated from work evidence, while activity logs preserve actor, action, source record, previous/new state, result, workflow, execution ID, and notes.

Control boundary

Native first. n8n where state crosses boards.

The architecture avoids external automation for simple Monday-native behavior. Cross-board controls are externalized only where the requirement needs validation or aggregation that cannot be safely enforced by a single board.

Mandatory project assignment

Every task must connect to a project. The Responsible person must be either that project's owner or a collaborator; ad hoc departmental work still receives a departmental project.

Due date vs scheduled work

Due dates remain deadlines. Personal calendar scheduling is optional and separate, allowing users to reserve work time without silently moving project or task deadlines.

Escalation evidence

Escalation requires a target person and note, and the resulting state is surfaced in recipient/leadership views.

One active session per user

Before a task starts or resumes, n8n queries active work sessions. A conflicting session blocks the new start instead of allowing overlapping time evidence.

Append-only session history

Pause and Complete close the current session. Resume creates a new session rather than reopening or overwriting historical rows.

Approved labor cost

Work sessions aggregate into period timesheets. Only approved hours become final labor-cost inputs, while rework remains separately measurable.
