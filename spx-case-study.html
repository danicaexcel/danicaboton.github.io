SPX Logistics Operations & Automated Encoding System

A first-mile logistics operations system that normalizes SPX activity, automates late-driver follow-up and escalation, generates hourly owner visibility, and isolates screenshot OCR as the next intake layer where direct SPX API access is unavailable.

Context

Operational pressure
and business risk

What needed to change

Admins continuously monitored the SPX mobile app, manually encoded operational updates into Excel, checked planned versus actual driver start times, called delayed drivers, monitored pickup progress and missed pickups, and sent hourly WhatsApp updates to the owner. Late starts could cause store closures, missed pickups, financial penalties, and delayed warehouse handovers, while repetitive monitoring consumed most of the admin team’s attention.

What I designed

I designed the system around a single normalized operational source of truth. Raw operational sheets were converted into an automation-safe driver-operation table, then self-hosted n8n ran a five-minute compliance monitor that compared planned and actual start times, sent WhatsApp follow-ups, limited retries to three attempts, and escalated unresolved drivers to admins. A separate hourly workflow aggregated active, delayed, completed, and escalated operations into a structured owner report.

Operational architecture

One source of truth.
Automation downstream.

The architecture intentionally avoids parallel spreadsheets or disconnected status reports. Monitoring, escalation, and owner reporting all depend on the same normalized operations record.

Implemented workflows

Routine supervision →
exception handling

Workflow 01

Driver Late Detection & Follow-Up

Every five minutes, n8n reads the normalized operations rows and checks whether planned start time has passed while actual start time is still blank. A late driver receives a WhatsApp follow-up. Followup Count increments until the maximum of three attempts is reached.

Escalation

Unresponsive Driver Path

After three unanswered follow-ups, the operation moves to an Unresponsive / Escalated state and the admin group is notified to intervene manually. The automation does not endlessly message the driver or hide the exception.

Workflow 02

Hourly Owner Operations Report

Every hour, n8n aggregates active drivers, delayed drivers, route assignments, escalation state, and operational progress into a structured WhatsApp update for the owner.

The automated encoder targets the work admins still do by hand.

SPX task screens contain operational values that admins currently read and encode manually. The screenshot encoder classifies the screen type, extracts the relevant fields, validates confidence and required values, and either writes an approved record or sends the capture to review.

Data normalization

Human-friendly sheet →
automation-safe contract

The spreadsheet structure was part of the engineering work.

The original workbooks contained merged cells, summary rows, inconsistent formatting, and layouts designed for people rather than automation. I separated that presentation layer from the operational automation layer.

  • One row = one driver operation.
  • No merged cells, title rows, or summary rows in the automation layer.
  • Predictable columns: Date, Driver Name, Phone, Route / Area, Planned Start Time, Actual Start Time, Actual End Time, Status, Followup Count, and Remarks.
  • Monitoring, escalation, and reporting all read the same row state.
  • The OCR extension writes to this same contract rather than adding a second operational database.

Reliability & controls

  • Single source of operational truth
  • Five-minute scheduled monitoring
  • Maximum three automated follow-ups
  • Human intervention only after escalation
  • Centralized status synchronization
  • Follow-up counters and status-change audit trail
  • OCR confidence + required-field validation
  • Human review for uncertain captures
  • Manual fallback when the SPX input cannot be reliably extracted

Outcome / current state

The implemented automation moved routine driver supervision and hourly management reporting out of manual admin work while preserving a clear human escalation path for real exceptions. Direct SPX API access was unavailable, so manual reading and encoding of SPX remained the final input dependency. The OCR encoder is reconstructed as the next phase: an ingestion adapter that can remove that encoding work while preserving the existing operational architecture.
