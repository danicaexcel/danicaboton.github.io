SPX Logistics Operations & Automated Encoding System

A first-mile logistics operations workspace that preserves the client’s familiar Daily Log and summary reporting while adding route progress, attendance, warehouse-trip handover and compensation, closing-time risk monitoring, owner visibility, WhatsApp escalation, and OCR-assisted SPX encoding.

Context

Business problem
and system response

What needed to change

Admins continuously monitored the SPX mobile app, manually encoded seller and pickup activity into Excel, watched store closing times, checked driver and assistant progress, followed up late teams, recorded missed pickups, logged warehouse handover trips, maintained attendance, calculated compensation inputs, and manually reported status to the owner.

What I designed

I organized those activities into one connected operations workspace. The Daily Log remains recognizable, while route progress, closing-time risk, attendance, trip handover, compensation, owner visibility, and audit history are derived around it. Self-hosted n8n handles scheduled monitoring, WhatsApp follow-up, escalation, synchronization, and hourly owner reporting. OCR-assisted encoding targets the remaining repetitive SPX screenshot-to-report step.

End-to-end journey

How a user works
through the system

From SPX screenshot to pickup completion, handover, and owner visibility.

This reconstructed journey shows how the admin, drivers/assistants, automation layer, and owner interact with the same operating records across a normal day.

01Admin

Open the day and review operating status

The admin starts in the Owner/Admin workspace, checks the Daily Log, route progress, attendance, open risks, pooled parcels, and the latest driver updates before new pickups are encoded.

System output: one operational picture of routes, people, pickup state, and exceptions.
02Admin · Encoder

Choose New Task or Task Update before uploading

For a new SPX pickup, the admin selects New Task. For a later screenshot of an existing pickup, the admin selects Task Update and chooses the existing Task ID. One screenshot is uploaded at a time.

Control: the admin explicitly chooses create vs update; the system does not guess from the filename.
03Encoder

Extract, classify, and validate the screenshot

The screenshot is classified by screen type, OCR text is parsed into known SPX fields, and required values are checked. Low-confidence or structurally inconsistent captures remain for review instead of being silently accepted.

System output: staged Task ID, seller, address, pickup counts, parcel state, timing, and validation status.
04Admin · Daily Log

Approve the staged record

After review, a New Task creates a new normalized Daily Log row; a Task Update applies the latest pickup/status values to the selected existing task. The source capture remains traceable for audit and troubleshooting.

System output: approved operational data becomes available to route, risk, pickup-pool, and reporting views.
05Driver + Assistant

Execute the assigned pickup

The team performs the route, while the operating record reflects assigned seller/store, route, pickup orders, scanned/picked parcels, on-hold state, remarks, and the responsible driver/assistant.

Operational evidence: the same pickup row drives route progress and parcel-risk visibility.
06Self-hosted n8n

Monitor compliance every five minutes

The automation checks whether expected driver activity is progressing and whether stores are approaching closing-time risk. It uses the operating records as the source for follow-up decisions.

Automation output: current compliance state, risk condition, and follow-up eligibility.
07WhatsApp + Admin

Follow up and escalate when needed

If a driver has not provided the expected update, the system sends bounded WhatsApp follow-ups. After the configured attempt limit, the issue is escalated to the admin instead of continuing indefinitely.

Control: up to three follow-up attempts before admin escalation.
08Driver + Admin

Record warehouse handover trips

When the van reaches the warehouse, the trip records route, trip number, driver, assistant, handed-over quantity, and unload state. Parcels not yet handed over remain visible in the pooled balance for the next trip.

System output: picked → handed over → remaining pooled is reconcilable by trip.
09Operations · Compensation

Turn verified handover into compensation input

Verified handed-over parcels become the pay basis. The represented rule is $0.03 per handed-over parcel, split 50/50 when both driver and assistant perform the trip, or 100% to the driver when working alone.

System output: trip-level evidence rolls into the daily compensation input.
10Owner

Receive hourly oversight without chasing the team

The owner sees route completion, closing-time risks, missed/unable pickups, driver/assistant state, warehouse handovers, pooled parcels, and the latest operational totals from the same underlying records.

Outcome: management visibility is derived from the work instead of a separate manual status report.
11Admin · End of day

Reconcile Daily Summary and exceptions

The admin closes the day by reviewing totals, unresolved pickup risks, remaining pooled parcels, attendance, handover quantities, compensation inputs, and any OCR or automation exceptions that still require correction.

Final state: Daily Log, Daily Summary, audit history, and owner reporting tell the same operational story.

Scope

What I built

The reporting workbook became an operating system.

Operations workspace
  • Preserved Daily Log fields for seller/store, closing time, route, driver/assistant, pickup orders, parcel state, remarks, and tally.
  • Route progress derived from the same pickup rows instead of a separate task tracker.
  • Closing-time risk for stores approaching missed-pickup conditions.
  • Driver and assistant attendance with login/logout evidence.
  • Warehouse handover trips with route, people, quantity, and unload state.
  • Compensation inputs based on verified handover quantity and participation.
Automation + encoding
  • Five-minute driver monitoring through self-hosted n8n.
  • WhatsApp follow-up with a three-attempt escalation boundary.
  • Hourly owner summary for progress, risks, driver state, and escalation status.
  • SPX Task Info and To-handover screenshot classification and extraction.
  • Confidence and structural validation before OCR-derived fields are accepted.
  • Exception/review handling and run evidence for troubleshooting.

Handover + pay

Trip evidence →
compensation input

Warehouse handover is both operational and financial evidence.

Each trip preserves the route, trip number, responsible driver, assistant, handed-over quantity, and unload state. Those verified quantities become the basis for compensation instead of an unrelated manually entered total.

Compensation rule represented: verified handed-over parcels × $0.03. When both driver and assistant perform the trip, the amount is split 50/50; when only the driver performs it, the driver receives the full trip amount.

Reliability & controls

Observable and
recoverable operations

The system is designed around evidence, limits, and review.

Operational controls
  • Bounded WhatsApp retries before escalation.
  • Separate attendance, route, trip, and compensation records.
  • Closing-time-sensitive risk evaluation.
  • Verified handover quantities before compensation input.
  • Owner summaries derived from operating records.
Encoding controls
  • Explicit New Task vs Task Update selection before upload.
  • Existing Task ID required for updates.
  • Screenshot classification before parsing.
  • Confidence and required-field validation.
  • Human review for uncertain extraction and source traceability.
